# Тест: map-reduce + thinking для таймшита

> Статус: **план, не реализован**. Цель — проверить, даст ли порционная
> обработка OCR с включённым thinking большую точность и чёткое разделение
> задач, чем текущий однопроходный пайплайн без thinking.
>
> Тест проводится **мимо ScreenMind**: напрямую против vLLM
> (`http://10.10.0.11:8000/v1`, модель `qwen3.5-9b`, окно 32 768 токенов).

---

## 1. Гипотеза

Текущий `_run_timesheet_mode` делает один вызов без thinking, где модель
просто заполняет бланк `ID | CUSTOMER | SUBJECT | JUSTIFICATION` по мешкам
изолированного текста. Это не даёт модели рассуждать о:

- **непрерывности задачи во времени** (последовательные скрины = одна задача);
- **работе внутри удалённых сессий** (Citrix: что делали внутри, а не имя хоста);
- **разделении составных окон** (один редактор — две задачи).

Порционная обработка (map) + связывание между скринами + повторный прогон
(reduce) с thinking должны дать более точные subject и честное разделение.

---

## 2. Что обязательно в дизайне (иначе тест невалиден)

### 2.1. Экспорт — с метаданными, не «голый OCR»
Номер тикета в ~90% случаев живёт в **заголовке окна** (`Ticket 99177 Details`),
не в OCR. Время — в timestamp. Клиент — в домене заголовка/OCR. Если выгрузить
только OCR, модель начнёт **выдумывать** номера тикетов и время.

Формат каждого блока в `.md`:

```
## SHOT 0042 | 2026-08-13T10:14:20 | Chrome | GITS PSF - HelpDesk - Ticket 99177 Details | https://support.gits.lu/...
<OCR-текст, сжатый пробелы, до ~1500 символов>
```

### 2.2. Резка порций — по временны́м разрывам, не по числу скриншотов
Пауза между кэпчами > 5–10 мин = естественная граница задачи. Резать по
количеству скриншотов — рвёт задачу пополам между порциями N и N+1.
Альтернатива: overlap — дублировать последние 3–5 скринов порции N в начало N+1.

### 2.3. Время считает код, не модель
На выходе map-шага модель отдаёт **сегменты с ID скриншотов**, а минуты
считает код из timestamp'ов (тот же `_span_minutes`). Если отдать модели и
время — воспроизведём старый баг автономного плагина, ради устранения которого
строилась архитектура «код владеет форматом».

Формат ответа модели на map-шаге:

```
SEGMENT | shots 40-52 | CUSTOMER | SUBJECT | EVIDENCE
```

## 3. Бюджеты токенов (механика vLLM)

- `max_tokens` в vLLM покрывает **thinking + контент вместе**.
- При thinking 7000 и окне 32k на вход остаётся ≤ ~24k токенов (~96k символов).
- Сырой OCR за день ~350k символов ≈ 84k токенов → **4–6 порций**.
- «Thinking limit 7000» — проверить, что vLLM умеет `thinking_budget` для
  qwen3.5 через `chat_template_kwargs`. Если нет — thinking жрёт сколько хочет,
  лимитом становится только `max_tokens`.
- Цена: 9B генерит 7k thinking-токенов последовательно → ~30–90 с на порцию,
  итого **5–15 минут на таймшит** против текущих ~13 с.

Формула входного бюджета на порцию:

```
вход = 32k − 7k (thinking) − ~1k (контент/резерв) ≈ 24k токенов ≈ 96k символов
```

---

## 4. Шаги теста

1. **Экспорт.** Выгрузить все analyzed-кэпчи за день в `.md` (формат §2.1),
   хронологически, с метаданными. Источник: `~/.screenmind/screenmind.db`.
2. **Разбивка.** Разрезать на порции по временны́м разрывам (§2.2), каждая
   ≤ ~96k символов входа.
3. **Map.** Каждую порцию — в vLLM с `enable_thinking: true`,
   `thinking_budget: 7000`. Просить: охарактеризовать деятельность, связать
   скрины в сегменты, вернуть строки `SEGMENT | shots | CUSTOMER | SUBJECT | EVIDENCE`.
4. **Reduce.** Все сегменты из всех порций — вторым вызовом: слить
   пересекающиеся/смежные сегменты одной задачи, убрать дубли, дать общий список.
5. **Подсчёт времени кодом.** Для каждого сегмента — минуты из timestamp'ов
   его скриншотов (`_span_minutes`), не из модели.
6. **Сравнение** с текущим выводом `_run_timesheet_mode` за тот же день (§5).

---

## 5. Метрики успеха

Запускать на **2026-08-13** (1223 кэпчи — самый богатый день) и 2026-08-14.

| метрика | как получить | что покажет |
|---|---|---|
| галлюцинации номеров тикетов | номера из вывода vs номера из заголовков окон (ground truth, детерминированный) | жёсткий pass/fail |
| точность клиентов | vs домены из OCR/заголовков | не ухудшил ли reduce |
| сумма минут | vs код-подсчёт | не «утекло» ли время |
| качество subject / разделение | вручную, вслепую A/B двух выводов | единственный софт-критерий |

**Критерий провала:** любой выдуманный номер тикета, которого нет в заголовках
окон за день → тест не доказывает точность, фиксируем галлюцинацию.

---

## 6. Известные риски

- **Thinking не чинит мусорный OCR** — он лишь увереннее галлюцинирует поверх
  него. Консерватизм текущего пайплайна частично защита от этого.
- **Малая модель с thinking на забитом контексте** чаще дрейфует по формату
  `SEGMENT | ...` — нужен строгий парсер и fallback.
- **Стоимость времени**: 5–15 мин на запуск. Для daily-агента терпимо, для
  интерактивного «Run Now» — нет.
- **Reduce-шаг может потерять клиентов**, если сегменты одной задачи пришли из
  разных порций с разными формулировками клиента.

---

## 7. Вердикт по идее

Тест стоит проводить — идея атакует реальные слабости текущей схемы
(нет связывания во времени, нет thinking, изолированные мешки текста).
Но валиден только с:

1. метаданными в экспорте (§2.1);
2. резкой по временны́м разрывам (§2.2);
3. временем, посчитанным кодом (§2.3).

В наивной форме («просто кормим голый OCR порциями») тест, скорее всего,
покажет **рост галлюцинаций**, а не точности.
